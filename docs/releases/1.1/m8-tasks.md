## T51 · 求好评（合规版）

- **背景**：上架至今 0 评价；评分/评论是搜索排名与转化信号（ASO 冷启动期尤其重要）。
- **触发（2026-10-11 拍板）**：累计**创建第 5 个 log 后**请求一次——覆盖**全部用户**（原方案"看解释/看总结"仅订阅用户可达，弃用）。
- **节流**：App 侧记录"已请求"，**请求后 90 天内不再请求**（即用户不会被打扰）。注意：弹不弹最终由 iOS 决定，开发者只能控制"请求"的频率；系统另有 365 天 3 次的硬限制。
- **入口**：设置页常驻「喜欢 Carelogue？去评分」→ App Store 评价页深链（`itms-apps://...?action=write-review`）。
- **红线**：不给任何回报/激励（Apple 明文禁止"激励评价"）；不用自定义弹窗假冒系统评分框。
- **验收**：触发路径在模拟器可验证（真实弹窗由系统决定，只在真机出现）；不打扰正常使用流。
- **✅ 代码完成（2026-10-11）**：`Services/ReviewPrompt.swift`——保存**新**记录且库内记录 ≥5、距上次请求 ≥90 天 → 记日期并在编辑器关闭 1.5s 后调 `AppStore.requestReview`；设置页常驻「喜欢 Carelogue？去评分」→ `apps.apple.com/app/id6815909128?action=write-review`。UI 测试 `ReviewPromptUITests`：第 5 条请求、第 6 条不请求、89 天不请求、91 天再请求（模拟器开发构建会真实弹出系统评分框，已截图验证）。
  - CC 自定：「第 5 个 log」按**库内总记录数 ≥5** 判断（老用户已有很多记录 → 下一次新建即请求一次），只在新建时触发，编辑不触发；App Store ID 由 bundle id 查得 `6815909128`。

## T52 · 复诊提醒（本地通知）

- **背景**：backlog「提醒（通知系统）——复诊 / 记录提醒」；本地通知，无需服务器。
- **方案**：
  - 用户开启提醒后调度本地通知；**时间点用户可自定义**（2026-10-11 拍板），默认值：**前一天 19:00 + 当天 08:00**，可改/可增删。
  - 通知内容：就诊名、时间、地点；中英随 app 语言。
  - 权限：**首次设置提醒时**请求通知权限（不在启动时弹）；被拒后设置页给引导文案。
  - 就诊时间修改/删除 → 通知同步重排/取消。
- **验收**：设置提醒后到点收到；改时间/删记录后通知同步；权限拒绝不崩、不影响其他功能。
- **✅ 代码完成（2026-10-11）**：就诊编辑器「提醒 · Reminder」（开关 + 多个「前 N 天 HH:MM」，打开时填入设置页默认值并首次请求权限）；设置页「提醒」卡（默认时间增删改 + 权限关闭引导）；即将就诊卡「已设提醒」pill。调度 = `Services/Reminders.swift`：每次保存/回前台从库里整体重排（改时间/删记录/归档旅程自动同步）。UI 测试 `ReminderUITests`（含真实到点横幅）全绿。
  - CC 自定：提醒只对「进行中」旅程的未来就诊生效；通知点开直达该就诊详情；提醒字段存 `Log.reminderJSON`（随自己 iCloud 同步，不进 CKShare）。
  - 卡外发现（未修，记录）：iOS 17.0 上 `ModelContext.didSave` 不发通知——`ShareChannel` 的「本地保存后 30s 推送」在 17.0 设备上不会触发（回前台仍会同步）。本卡的调度器已同时监听 Core Data 的保存通知规避；ShareChannel 是否同样处理待定。

- **背景**：backlog「用药计划 + 服药提醒」；与 T52 打包成同一套提醒系统。
- **方案**：
  - 新增模型 `Medication`（名称、剂量文本、提醒时间点集合）——**schema 新增**（CloudKit 兼容要点照 CLAUDE.md）。
  - **入口（拍板）**：**全局**（设置/主页一级入口）；每条用药**可选关联一个 journey**（associate）。

## T54 · Apple Health 集成

- **背景**：测量数据手输麻烦；HealthKit 读写可省事，且是 Apple 生态差异化的第一步。
- **方案**：
  - **读**：体重、血压、心率（以及孕期相关可读项）→ 按用户选择同步进 journey 的测量时间线。
  - **写回 Health（拍板）**：做；用户可关闭，**默认开启**。
  - **注意（5.1.3(ii)）**：条款「不得将个人健康信息存 iCloud」的适用范围未定（详见 `docs/legal/app-review-513-ii-icloud.md`）；**HealthKit 读入数据的同步策略开工前单独评估**。
  - **前置条件**（三项都办才能上）：
    1. 隐私政策加 **HealthKit 使用章节**（Apple 强制要求，`docs/legal/privacy-policy.md` + 线上 `carelogue.ca/privacy`）；
    2. 隐私标签复核（数据仅设备上处理、不进服务器——"不收集"结论大概率维持，但要重走一遍）；
    3. 权限文案 + 选择性授权（只读用户勾选的类型）。
- **验收**：授权后 Health 里已有的体重出现在时间线；拒绝授权不影响其他功能；写回开关可关。
- **✅ 代码完成（2026-10-11）**：`Services/HealthSync.swift` + `Views/HealthLinkSheet.swift`。旅程「…」→「Apple 健康」：勾选体重/血压/心率/体温（默认体重+血压）→「连接并导入」→ 系统授权页**只请求读取勾选的类型**（写入：写回开启时请求四类）→ 导入旅程起点（T56 起点，否则创建日）至今的读数成为该旅程的测量记录；之后每次打开该旅程自动增量导入；「停止读取」保留已导入记录。去重 = 新字段 `Log.healthSampleID`（`in:`/`out:` + HealthKit UUID，跨旅程、不进 CKShare）。写回：设置 › Apple 健康 ›「写入 Apple 健康」（默认开）——在 Carelogue 保存的四类测量写入「健康」，编辑即替换、删除即移除；从「健康」导入的读数不回写；无写权限时静默跳过、不弹窗。新增测量预设「心率」(bpm)。心率读取**每日静息心率**（原始心率每天上千条会淹没时间线）。
  - 验证：`HealthUITests`（模拟器真实 HealthKit：授权页 → 导入 3 条体重 + 1 条血压 → 再连接不重复 → 新建体重写入「健康」→ 删除后「健康」里也没了），英文 `testEnglishHealthSheetHasNoChineseCopy`；拒绝授权路径：读取被拒时 HealthKit 只返回空结果（系统设计，不暴露是否被拒），导入 0 条、不影响其他功能。
  - **前置三项**：① 隐私政策已加 HealthKit 章节（+ 提醒 / Apple 地图联想 / 小组件），`docs/legal/privacy-policy.md`，生效日期改为 2026/10/11，server 测试 63/63 通过——**线上需老板 `cd server && npm run deploy`**；② 隐私标签复核（CC 结论）：健康读数只在设备 + 用户自己的 iCloud 私有库，不传给开发者/第三方；地点联想的查询词发给 Apple 自家服务；Widget 数据在本机 App Group——按 Apple「收集 = 传出设备且开发者/第三方可访问」口径，**维持 Data Not Collected**，老板在 ASC 过目确认即可；③ 权限文案（`NSHealthShareUsageDescription` / `NSHealthUpdateUsageDescription`，中英）+ 选择性授权 ✅。
  - **老旅程 gap 修补（2026-10-11，老板「都修」）**：① **单位**——写回按单位换算成「健康」的单位（kg/lb/磅/斤/g、°C/°F、mmHg/kPa、bpm），**不认识的单位不写回**（之前 140 lb 会被写成 140 kg）；导入按该旅程该类型已用的单位换算（记 lb 的旅程导入也是 lb）；② **重复**——导入时与手动记录比对：同类型、数值相同（按「健康」单位比）、时间相差 ≤15 分钟视为同一次读数，跳过并把手动那条标记为来自「健康」（以后不会被写回成第二份）；1.0 的单值血压只比收缩压；③ **导入起点**——不再绑定目标日：连接页「从哪天开始读取」= 从旅程开始（默认）/ 提前 3 个月 / 提前 1 年 / 全部历史。测试 `HealthUITests` 新增 3 例（换算与未知单位、lb 旅程导入 + 跳过手动重复、提前起点补读）。
  - ⚠️ **提审风险（需老板知悉/决定）**：App Review Guideline 5.1.3(ii) 写明「may not store personal health information in iCloud」。Carelogue 1.0 已把健康记录存在用户 iCloud 私有库并已过审；接入 HealthKit 后审核通常更严，**从「健康」导入的读数同样会随 CloudKit 同步**。若被拒，可选方案：(a) 导入的读数只存本机（需一个不同步的独立 store，改动较大）；(b) 只做写回、不做读取。本批按卡片方案实现，未做规避。

## T61 · 旅程「记录对象」（2026-10-11 追加，随 1.1）

- **背景**：T54 上线前的走查——共享旅程里「创建者」≠「记录的是谁的身体」（如：丈夫创建孕期旅程、记录对象是太太）。现状下 Apple 健康写回发生在**录入的那台设备**：丈夫替太太记的血压会写成丈夫自己的健康数据（错误数据，且触 5.1.3(ii)「不得写入不准确的健康数据」）；同类问题：AI 解释「附带档案」发出的是本机主人的过敏/用药，而非记录对象的。
- **方案（拍板 2026-10-11：随 1.1；身份绑定由 CC 定 = 名字 + iCloud 身份）**：
  - Journey 新增可选字段 `subjectName`（显示名，如「太太」）+ `subjectUserID`（记录对象本人的 CloudKit 用户 ID；无 iCloud 时为本机安装 ID）；随 CKShare 同步。通用字段，任何旅程适用。
  - 三种对象：我自己 / 共享成员（从参与者里选）/ 其他人（只填名字，如没有手机的孩子）。在「概要与目标日」编辑器里设置；新建向导不加步骤。
  - **老旅程**：字段为空 =「未指定」；首次在该旅程连接 Apple 健康时确认「这段旅程记录的是你本人吗？」→ 是则记录对象设为本机主人。
  - **规则**：① Apple 健康连接 / 导入 / 写回只在记录对象本人的设备上；写回改为**按旅程**（该设备在该旅程连接过才写回；设置里的开关为总开关）；② AI 解释「附带档案」只在记录对象是本人或未指定时附带；③ 头部显示记录对象（他人时）。
  - 连接页写明：「Apple 健康里的数据属于这台 iPhone 的主人，只在这段旅程记录的是你本人时连接」；共享旅程补一句「其他成员录入的测量不会写入你的『健康』」。
  - 顺带修 T54 遗留：共享成员**修改**了记录对象写入「健康」的测量 → 对象设备下次打开该旅程时把「健康」里那条更新为新值。
- **验收**：未指定旅程连接健康时有确认、确认后对象 = 我；对象为他人/其他人时连接不可用并说明原因；未连接的旅程录入测量不写回；AI 档案规则生效；共享成员可选；中英；老旅程不受影响。
- **✅ 代码完成（2026-10-11）**：`Services/JourneySubject.swift`（本机身份 `MyIdentity`：iCloud 用户 ID，无 iCloud 用本机安装 ID；`Journey.subject` = 未指定 / 我 / 他人；共享成员列表取自 CKShare 参与者）；编辑器「记录对象 · Whose journey」（未指定 / 我自己 / 共享成员 / 其他人 + 称呼）；头部 chip「记录对象 太太」（他人，或共享旅程里的「我」）；Apple 健康页首段写明数据归属，共享旅程补「其他成员录入的不会写入你的『健康』」，未指定时连接前确认认领，他人旅程连接不可用并说明；`HealthSync` 写回改为按旅程（该设备连接过才写）、对象改为他人时自动停止读取、打开旅程时把被共享成员改过的写回同步到「健康」；`ExplainService` 附带档案只用于非他人的旅程；隐私政策同步两处。CKShare 通道 + ckdb 加两字段（随 owner-actions 的共享 schema 一并部署）。
  - 验证：`JourneySubjectUITests` 4 例（认领、其他人不可连、共享成员「太太」、只在已连接旅程写回）+ `ExplainUITests.testProfileOnlyForMyOwnJourney`（本人旅程带档案、他人旅程不带）；T54 的 `HealthUITests` 改为先认领。
  - CC 自定：身份 = 名字 + iCloud 身份（老板授权）；认领「我自己」时名字取 CKShare 里的本人姓名（拿不到则对方看到「其他成员」）；选「其他人」必须填称呼才可保存。
